# M04 Demo Project — Адаптивная вёрстка и доступность

Компактный plain HTML/CSS пример, демонстрирующий технические механизмы темы M04.

**SOLUTION BOUNDARY: PARTIAL_REFERENCE_IMPLEMENTATION.**

Проект содержит одну representative page и **не является** готовым `kr3-responsive-shop`: в нём нет полного набора страниц КР №3, готового Lighthouse-отчёта, итогового README студента или самостоятельной доработки.

Откройте `index.html` напрямую либо запустите локальный статический сервер:


## CSS breakpoints проекта

В проекте **два breakpoint**:

| Breakpoint | Значение | Пиксели | Что меняется |
|---|---|---|---|
| Базовая версия | — | 0+ | Одна колонка, вертикальная навигация, форма в 1 колонку |
| Первый breakpoint | `min-width: 768px` | ≥ 768 px | Навигация горизонтально, hero центрируется, 2 колонки товаров, форма 2 колонки |
| Второй breakpoint | `min-width: 1200px` | ≥ 1200 px | Sidebar + 3 колонки товаров, sticky фильтр, форма 3 колонки, 4 шага аудита в ряд |

### Почему в demo используются px и связь с rem

В данном учебном demo media queries записаны в **пикселях (`768px`, `1200px`)** для прямой и однозначной связи с материалами практических занятий (в частности, практического занятия №12 курса).

**Учебный характер решения:**
Выбор `px` в данном demo является **учебным решением** для простоты сверки с практическими заданиями, а **не универсальным правилом CSS**. В продакшене и реальных проектах точки перелома часто задают в `rem` (например, `48rem ≈ 768px` и `75rem ≈ 1200px` при базовом размере шрифта 16px):
- `rem` автоматически масштабирует сетку при изменении пользователем размера шрифта по умолчанию в браузере или ОС;
- `px` удобен в обучении благодаря точному и прозрачному сопоставлению с контрольными точками макетов.

Оба варианта синтаксически корректны в CSS. Выбор конкретных единиц — вопрос командных соглашений и требований проекта.

### Почему `min-width`, а не `max-width`?

Mobile-first: базовые стили написаны для узкого экрана. `min-width` **добавляет** компоновку для широких экранов, не отменяет её. Это проще и надёжнее, чем начинать с десктопа и «откатывать» стили.

### Content-driven breakpoints

Значения 768px и 1200px выбраны в точках, где **содержимому требуется другая компоновка**, а не потому что это размеры конкретного телефона или планшета. Рынок устройств постоянно меняется — привязка к конкретным моделям ненадёжна.

## Механизмы, демонстрируемые в проекте

### Адаптивные изображения (`<picture>`, `srcset`, `sizes`)

Раздел «Адаптивные изображения» в `index.html` показывает:

- `<picture>` — контейнер, в котором браузер перебирает `<source>` и выбирает подходящий.
- `<source media="...">` — art direction: разные изображения для разных диапазонов viewport.
- `srcset` — список вариантов с дескрипторами ширины (`480w`, `960w`).
- `sizes` — подсказка браузеру, какую долю экрана займёт изображение.
- Fallback `<img>` — обязателен; отображается если ни один `<source>` не подошёл.

Проверка: DevTools → Network → фильтр «Img», менять ширину окна. Или в консоли: `document.querySelector('.resp-img-demo__image').currentSrc`.

| Ширина viewport | Загружаемый файл | Почему |
|---|---|---|
| < 480 px | `workspace-mobile.svg` (480×560, вертикальная) | Art direction: портретная композиция для узкого экрана |
| 480–959 px | `workspace-480.svg` (480×320, горизонтальная) | Art direction: компактная горизонтальная для среднего viewport |
| ≥ 960 px | `workspace-960.svg` (960×640, широкая) | Fallback `<img>` + srcset |

### Доступность изображений: смысловой и декоративный `alt`

В проекте строго соблюдается правило доступности изображений:
- **Смысловой `alt="..."`**: обязателен для изображений, несущих информационную ценность (контентных иллюстраций, карточек товаров, схем). Скринридер зачитывает этот текст незрячему пользователю, передавая суть изображения (например, в каталоге: `alt="Синяя настольная лампа на рабочем столе"`).
- **Декоративный `alt=""` (пустой)**: используется для чисто оформительских изображений (фоновые плашки, абстрактные иконки, декоративные разделители или иллюстрации, дублирующие текст подписи). Пустой атрибут явно сообщает браузеру и скринридеру, что изображение декоративно и его нужно пропустить. Полное отсутствие атрибута `alt` является грубым нарушением доступности (скринридер будет читать техническое имя файла или URL).

### Доступность формы и демонстрация ошибки

В проекте продемонстрированы базовые и расширенные механизмы доступности форм:
- **Связка `<label for="...">` ↔ `<input id="...">`**: для каждого поля обеспечена программная связь, позволяющая вспомогательным технологиям объявлять название поля при фокусе.
- **Статический учебный пример ошибочного состояния**:
  - `aria-invalid="true"` — сообщает скринридеру о некорректном значении в поле;
  - `aria-describedby="error-email-msg"` — связывает поле с текстом ошибки, благодаря чему сообщение зачитывается сразу после подписи поля;
  - `role="alert"` — объявляет блок ошибки live-регионом;
  - Селектор `.field input[aria-invalid="true"]` в CSS визуально выделяет ошибочное поле.

> **Важно:** в учебном demo это демонстрационное статическое состояние разметки без JavaScript-валидации. В реальном интерфейсе атрибут `aria-invalid="true"` и блок с текстом ошибки появляются динамически только после валидации (при попытке отправки формы или событии blur).

### Container Queries — дополнительный механизм

> **Container Queries демонстрируются как дополнительный современный механизм темы, но НЕ являются обязательным требованием контрольной работы №3. Базовая компоновка остаётся полностью работоспособной без Container Query.**

Карточка товара (`.product-card`) меняет внутреннюю компоновку — изображение переходит из позиции «сверху» в позицию «слева» — когда её контейнер `.product-shell` становится шире `32rem`.

**Ключевое различие:**
- `@media (min-width: 768px)` — реагирует на ширину **всего viewport**. Применяется везде одновременно.
- `@container (min-width: 32rem)` — реагирует на ширину **конкретного контейнера** (`.product-shell`). Карточка в узком сайдбаре остаётся вертикальной, даже если viewport широкий.

`container-type: inline-size` объявляет элемент containment-контейнером по горизонтальной оси. Без этого объявления `@container` на дочерних элементах не работает.

### Другие механизмы

- **Flexbox**: шапка, навигация, кнопки, форм-действия, диалог.
- **CSS Grid**: каталог, сетка товаров, форма, шаги аудита.
- **Skip-link**: первый `Tab` показывает ссылку «Перейти к основному содержимому».
- **Адаптивная таблица**: `min-width: 42rem` + `overflow-x: auto` на `.table-scroll` — локальный горизонтальный скролл без скролла всей страницы.
- **`overflow-wrap: anywhere`**: предотвращает переполнение карточки длинными неразрывными строками (URL, идентификаторы) без создания горизонтального скролла страницы.
- **`position: sticky`**: фильтр «прилипает» при ≥ 1200px.
- **`:focus-visible`**: видимый фокус при навигации с клавиатуры.
- **`prefers-reduced-motion`**: отключает `scroll-behavior: smooth` при системной настройке.
- **`:has()`**: переключение состояния аудита «до/после» через CSS без JS.
- **`<dialog>`**: модальное окно с управлением фокусом.

Lighthouse-отчёт в проект не включён: допустим только отчёт, фактически полученный из актуального состояния проекта. Manual checks и browser measurements выполняются независимо от Lighthouse.
